# 玄枢移动端产品现状审计与下一阶段计划

日期：2026-07-21

## 1. 结论先行

玄枢目前已经具备一个可演示的移动 H5 产品外壳：视觉体系基本统一，首页、档案、生辰、星座、紫微、完整星盘、问答、合盘、分享图、工具中心和个人中心都已经有页面或流程，工程构建和现有自动化测试也能通过。

但它还不能直接按“面向真实用户的市场版本”继续扩功能。当前最需要解决的不是再增加塔罗、测试或更多报告，而是四类基础问题：

1. **用户身份和档案状态不可信**：无档案时可直接看到一份被包装成“自己”的完整示例报告。
2. **资料完整度没有形成统一能力边界**：只填称呼即可保存，但回到首页会直接崩溃；资料不足时部分报告仍输出看似精确的结论。
3. **报告内部存在数据矛盾**：同一份生辰报告同时出现“甲木”和“庚金”；星盘资料不足时仍展示宫位和角度相关结论。
4. **功能入口和产品结构开始重复**：报告中心、工具中心、首页和底部导航之间互相重复，用户不容易理解“报告”和“工具”的区别。

因此下一阶段必须先做“数据真实性与主流程硬化”，再做信息架构和内容压缩，最后才进入新功能扩展和正式后端上线。

## 2. 本次审计方法

本次不是只读代码，而是使用全新浏览器来源分别模拟：

- 第一次打开且没有档案的用户
- 创建完整档案的用户
- 只保存称呼的资料不完整用户
- 直接通过 URL 进入报告的用户
- 生辰、星座、紫微和完整星盘阅读用户
- 创建双人合盘的用户
- 使用问题解读的用户
- 进入工具中心和个人中心的回访用户

同时检查了相关组件、数据适配层、算法封装、现有测试、生产构建和静态部署边界。

证据截图位于：`output/product-audit-2026-07-21/`。

## 3. 当前产品结构

### 3.1 品牌与公开信息层

- 品牌官网首页
- 关于玄枢
- 隐私政策
- 使用条款

### 3.2 移动 H5 产品层

- `/m`：首页与首次引导
- `/m/create`：创建档案
- `/m/generating`：报告生成过渡
- `/m/report`：报告中心
- `/m/report/bazi`：生辰报告
- `/m/report/zodiac`：星座人格报告
- `/m/report/ziwei`：紫微报告
- `/m/report/flow`：流盘报告
- `/m/chart`、`/m/chart/natal`、`/m/chart/transit`：完整星盘
- `/m/chat`：结构化问题解读
- `/m/compatibility`：合盘入口、创建、生成、结果和历史
- `/m/tools`：工具中心
- `/m/profile`：档案、报告记录、分享记录和本地/云端状态

### 3.3 服务端与管理层

动态构建中已经存在：

- 注册和登录接口
- 档案与同步接口
- 报告、问题解读、分享图和埋点接口
- `/admin` 管理页面
- JSON 文件数据存储

静态 GitHub Pages 版本不具备这些服务端能力，只能使用本地档案、本地报告和本地分享功能。当前必须把“静态体验版”和“真实账号版”当成两种明确产品形态，不能在同一个页面里混合暗示。

## 4. 当前能力真实性矩阵

| 模块 | 当前级别 | 现状判断 |
| --- | --- | --- |
| 首次进入 | REAL_LOCAL，但有阻断缺陷 | 欢迎页存在，但底部导航可绕过流程 |
| 游客档案 | REAL_LOCAL，但状态模型错误 | 本地存储可用；无档案会被默认示例档案替代 |
| 三步创建 | REAL_LOCAL，但流程不完整 | 页面看似三步，实际每一步仍显示全部字段 |
| 今日观察 | REAL_LOCAL | 本地规则库稳定选择，同日刷新不变；依赖有效出生日期 |
| 生辰排盘 | REAL_LOCAL | 使用真实日历/八字数据，但封面仍有硬编码冲突 |
| 星座人格 | REAL_LOCAL / PARTIAL | 有实际星体计算和内容层；资料不足边界仍需收紧 |
| 完整星盘 | REAL_LOCAL / EXPERIMENTAL | 可绘制星盘，但“今日行星”、宫位和行运语义不严谨 |
| 紫微排盘 | REAL_LOCAL + STATIC_CONTENT | iztro 输出真实结构；部分首屏结论和十二宫视觉是固定内容 |
| 流盘 | REAL_LOCAL / PARTIAL | 有真实时间结构，但解释层需要明确依据和边界 |
| 问玄枢 | REAL_LOCAL | 规则型问题解读，不伪装实时 AI，是目前较完整的产品闭环 |
| 合盘 | EXPERIMENTAL_LOCAL | 有双方计算和报告结构，但档案解析会失败，评分为自定义启发式规则 |
| 分享海报 | REAL_LOCAL | 已验证可生成 1080×1920 PNG；真机系统分享仍需继续验证 |
| 云端登录与同步 | REAL_API，仅动态部署 | 静态部署不可用；当前邮箱密码方案与国内手机用户习惯未最终对齐 |
| 后台管理 | DEVELOPMENT_MVP | 有页面和接口；JSON 文件存储不适合多实例和正式并发 |
| 塔罗、灵数、测试等扩展 | PLANNED | 目前不应优先实现 |

级别定义：

- `REAL_LOCAL`：浏览器本地真实运行，可离线或静态部署使用
- `REAL_API`：依赖服务端接口
- `PARTIAL`：部分输入或结果可用，但存在资料能力限制
- `EXPERIMENTAL_LOCAL`：真实代码运行，但规则尚未达到正式产品可信度
- `STATIC_CONTENT`：视觉或文案存在固定示例内容
- `PLANNED`：尚未实现

## 5. 实际用户路径判断

### 5.1 第一次打开：黄色

优点：

- “创建我的档案”和“先看示例”两个方向容易理解。
- 没有一上来强制登录。
- 产品定位和隐私说明比较克制。

问题：

- 欢迎状态仍显示完整底部导航，用户可以绕过建档进入报告中心。
- 绕过后系统会静默使用默认示例档案，却没有明确告诉用户。

证据：[01-first-open.png](../output/product-audit-2026-07-21/01-first-open.png)

### 5.2 创建档案：红色

优点：

- 字段基本覆盖称呼、性别、历法、出生日期、时间和地点。
- 对未知时辰和地点影响有解释。

问题：

- “三步”只是标题和高亮变化，所有字段每一步都同时可见，用户连续点击“继续”却没有真正减轻认知负担。
- “先保存基础资料”允许只填称呼；保存后首页无条件计算今日观察，导致整个页面崩溃。
- 完成后固定进入生辰报告，无法恢复用户从星盘、紫微或合盘进入时的原始意图。

## 6. 必须修复的问题清单

### P0：不修不能继续对外测试

1. **移除无档案自动回退为完整示例档案的行为。**
2. **增加统一路由能力守卫**，禁止无档案直接进入个人报告；示例必须由用户主动选择。
3. **修复“只保存基础资料”导致首页崩溃。**
4. **把档案状态改为显式状态机**：首次访问、示例、草稿、本地完整、云端绑定。
5. **建立报告能力矩阵**，根据出生日期、时辰、地点、性别和双方档案决定“可用/部分可用/需补资料”。
6. **修复生辰五行圆环的硬编码日主。**
7. **修复合盘创建页与生成页使用不同档案来源的问题。**
8. **修复星盘资料不足时仍输出宫位、上升、天顶及相关相位的问题。**
9. **把紫微固定文案和真实盘面明确分开**，禁止固定结论冒充个人计算结果。
10. **为上述问题增加自动化回归测试**；现有 43 个测试全部通过，但没有覆盖这些真实用户路径。

### P1：完成 P0 后优化主流程

1. 把创建档案改为真正三步，每一步只显示当前字段。
2. 用 `returnTo` 或 `intent` 恢复用户原始入口，不再固定生成生辰。
3. 示例档案全局持续标识为“示例：小玄”，并提供“创建我的档案”。
4. 精简首页，只保留今日观察、一个主要问题链和继续阅读。
5. 重组底部导航与信息架构，去掉报告和工具的重复入口。
6. 生辰长报告增加章节导航、阅读进度和继续阅读位置。
7. 星座首屏降低信息密度，未开放体系移入工具中心。
8. 把“今日行星”明确改名为“今日天象”；真正行运另建叠盘能力。
9. 紫微实现真实宫位可视化，或把当前固定图更名为“领域导航示意”。
10. 合盘复用统一档案编辑器，删除暂不参与计算的 MBTI 字段。
11. 合盘弱化单一总分，突出吸引、沟通、情绪、价值观、节奏和冲突等维度。
12. 每个报告首屏显示“依据哪些资料”和“哪些资料尚未参与计算”。

### P2：市场交付与扩展

1. 决定正式登录方案：手机号验证码、微信授权、邮箱，或组合方案。
2. 把 JSON 数据存储迁移到 PostgreSQL 等可靠数据库。
3. 明确静态体验版和动态账号版的部署策略。
4. 完成真实 iPhone Safari、微信 iOS、Android Chrome、微信 Android 验证。
5. 对出生日期、时间、地点等个人信息做正式隐私合规审查。
6. 增加账号删除、档案删除、数据导出、同步冲突和数据保留策略。
7. 增加错误监控、性能监控、备份和回滚。
8. 完成真实算法金标准样本和跨引擎回归验证。
9. P0/P1 稳定后，再按优先级加入塔罗、灵数、测试和内容发现。

## 7. 推荐的信息架构

底部导航继续保持四项，但职责必须重新定义：

### 首页

- 当前档案与资料状态
- 今日观察
- 一个核心问题入口
- 继续上次阅读

首页不再陈列完整报告目录和大量重复问题。

仅放“基于单个档案、可长期保存的计算结果”：

- 星座人格
- 完整星盘
- 紫微
- 流盘

每项根据能力矩阵显示：可使用、部分可用、需补资料或示例。

### 工具

仅放“需要用户执行一次任务的流程”：

- 问玄枢
- 合盘
- 后续塔罗
- 后续测试
- 后续灵数与其他实验工具

完整星盘和报告中心不再重复出现在工具页。

### 我的

- 当前档案
- 多档案和关系档案
- 报告历史
- 合盘历史
- 问题历史
- 分享记录
- 本地/云端状态

## 8. 推荐的统一档案状态模型

当前问题的根本原因是“没有档案”和“默认示例档案”共用同一个对象。建议改为显式联合状态：

```ts
type ProfileState =
  | { kind: "empty" }
  | { kind: "demo"; profile: MobileProfile }
  | { kind: "draft"; profile: Partial<MobileProfile>; missing: ProfileField[] }
  | { kind: "local"; profile: MobileProfile }
  | { kind: "cloud"; profile: MobileProfile; syncStatus: SyncStatus };
```

所有报告先读取能力，而不是直接读取一个永远存在的 `profile`：

```ts
type ReportCapability = {
  level: "unavailable" | "partial" | "full";
  missing: ProfileField[];
  reasons: string[];
};
```

建议最低能力规则：

| 报告 | 最低资料 | 部分可用规则 |
| --- | --- | --- |
| 今日观察 | 有效出生日期 | 无日期不可计算 |
| 生辰 | 有效日期 | 未知时辰时不生成时柱确定结论 |
| 星座人格 | 有效日期 | 月亮临界日需提示；无时辰不生成上升 |
| 完整星盘 | 日期、精确时间、地点 | 资料不足仅显示可确认的行星星座 |
| 今日天象 | 当前日期 | 不显示个人宫位和上升/天顶相位 |
| 真正行运 | 完整本命盘 + 当前时间 | 需实现当前行星与本命盘叠加关系 |
| 紫微 | 日期、时辰、性别 | 资料不足时只显示补充资料页 |
| 合盘 | 两份满足所选模式的档案 | 任一档案不足时显示缺失项，不进入生成页 |

## 9. 算法与开源依赖建议

### 继续保留

- `lunar-javascript`：用于公历/农历、干支、节气和八字等基础数据，MIT 许可，功能与当前项目契合。[官方仓库](https://github.com/6tail/lunar-javascript)
- `iztro`：用于紫微排盘，MIT 许可，能输出十二宫、运限和四化等结构；项目应继续通过适配层隔离第三方数据。[官方仓库](https://github.com/SylarLong/iztro)

### 需要技术验证后再决定

- 当前 `circular-natal-horoscope-js` 可以继续作为现状基线，但不能在没有金标准回归样本的情况下直接认定适合正式市场。
- 可做一个独立技术实验，用 [Astronomy Engine](https://github.com/cosinekitty/astronomy) 计算和校验太阳、月亮及行星位置。它强调使用 VSOP87/NOVAS 模型，并对 JPL Horizons 等来源做测试，但它不是完整占星宫位/解读库。
- [AstroChart](https://github.com/AstroDraw/AstroChart) 只负责 SVG 星盘渲染，不计算行星位置；可以作为渲染层候选，不能替代计算引擎。

正确的星盘架构应是：

```text
天文位置计算/验证
→ 占星坐标与宫位规则
→ 标准化 NatalChart / TransitChart
→ SVG/Canvas 渲染
→ 中文内容解释层
```

不要再让一个第三方库的原始对象直接控制页面文案。
